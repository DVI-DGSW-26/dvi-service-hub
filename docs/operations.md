## 0. 먼저 알아 둘 것

**운영 주소는 `https://service-hub.dvi-ind.com` 입니다.**
예전 주소인 `dvi-service-hub.vercel.app` 으로 들어오면 같은 경로의 새 주소로 자동으로 넘어갑니다.

**`dev` 브랜치에 push 하면 곧바로 운영에 배포됩니다.**
따로 검증 단계가 없습니다. Vercel 미리보기(Preview) 배포는 가짜 데이터로만 뜨기 때문에,
로그인이 제대로 되는지는 운영에 낸 뒤에야 확인할 수 있습니다. 그래서 배포 직후 점검이 중요합니다.

허브는 다음 네 곳에 기대어 돌아갑니다.

| 구성 요소 | 하는 일 | 주소 |
| --- | --- | --- |
| Vercel | 화면을 내보내고, 로그인 검사와 세션 갱신을 맡습니다 | `service-hub.dvi-ind.com` |
| Keycloak | 사내 통합 로그인입니다 | `api.dvi-ind.com/dauth/realms/dvi` |
| 허브 서버 | 공지, 일정 같은 위젯 데이터를 줍니다 (service-hub-server) | `api.dvi-ind.com/hub` |
| 정적 파일 서버 | 다른 서비스에 붙는 "서비스 이동 버튼" 파일(switcher.js)을 내보냅니다 | `api.dvi-ind.com/static/switcher/` |

모바일 앱(`apps/mobile`)은 운영 주소를 그대로 띄우는 Android 껍데기라서, 웹을 배포하면 앱 화면도 함께 바뀝니다.

## 1. 문의를 받았을 때

### 1.1 먼저 해 볼 것

1. **강력 새로고침**을 부탁합니다. PC 는 `Ctrl + Shift + R`, 휴대폰은 앱이나 탭을 완전히 닫았다가 다시 엽니다.
2. 그래도 안 되면 PC 에서 **F12 를 눌러 Console 탭**을 열고, 빨간 줄을 캡처해 달라고 합니다.
3. 캡처에서 두 가지를 찾습니다.
   - `from=` 뒤에 오는 말: 누가 낸 오류인지 알려 줍니다.
   - `#` 뒤에 오는 8글자(예: `#a1b2c3d4`): 서버 로그를 찾는 번호입니다.
4. 그 번호로 Vercel 로그를 찾습니다([5.2](#52-vercel-로그)). Vercel 로그는 오래 남지 않으니 **그날 안에** 봅니다.
5. 원인에 맞는 담당자에게 넘깁니다([10. 연락처](#10-연락처)).

### 1.2 증상별로 보기

**화면이 하얗게 나오는데, 강력 새로고침하면 뜬다**

- 원인: 기기에 저장해 둔 화면 파일이 오래됐거나 깨졌습니다.
- 조치: 한 사람이면 강력 새로고침으로 끝납니다. 여러 사람이 같은 증상이면 [6. 서비스 워커 긴급 정지](#6-서비스-워커-긴급-정지)를 합니다.

**로그인 화면이 자꾸 다시 뜬다, 또는 "로그인을 이어가지 못했습니다"가 보인다**

- 확인: Vercel 로그에서 `refresh.rejected` 줄의 `detail` 을 봅니다.
- `Session not active` 처럼 통합 로그인이 끝났다는 내용이면 정상입니다. 다시 로그인하면 됩니다.
- refresh token 재사용(reuse)에 관한 내용이 자주 보이면, 여러 탭이 동시에 세션을 늘리다 부딪힌 것입니다. 허브 담당자에게 넘깁니다.

**위젯이 모두 "불러오지 못했어요"로 나온다**

- 확인: 콘솔의 `from=` 을 봅니다.
- `from=hub-server` 이면 허브 서버 문제입니다. 허브 서버 담당자에게 넘깁니다.
- `from=vercel` 이면 Vercel 이 허브 서버에 닿지 못한 것입니다. [8. 가동 감시](#8-가동-감시) 주소에서 `hubServer` 값을 확인합니다.

**허브에는 로그인돼 있는데 위젯만 401 이 난다**

- 확인: 콘솔에 "허브 로그인은 살아 있는데 허브 서버가 쿠키를 받지 않습니다"라는 노란 줄이 있습니다.
- 원인: Vercel 과 허브 서버의 `SESSION_SECRET` 값이 서로 다릅니다.
- 조치: [7. 비밀값 바꾸기](#7-비밀값-바꾸기)의 순서대로 두 곳을 같은 값으로 맞춥니다.

**아무도 로그인하지 못한다**

- 확인: [8. 가동 감시](#8-가동-감시) 주소에서 `keycloak` 값을 봅니다.
- 원인: 통합 로그인(Keycloak)이 멈췄을 가능성이 큽니다. Keycloak 담당자에게 넘깁니다.
- 참고: 이미 로그인한 사람은 세션이 남아 있는 최대 10분 동안은 계속 쓸 수 있습니다. Keycloak 에 닿지 못해 갱신이 실패한 경우에는 세션을 지우지 않습니다.

**"로그인하지 못했습니다" 화면이 나온다**

- 확인: Vercel 로그에서 `auth.error_page` 줄의 `who` 를 봅니다.
- `keycloak` 이면 통합 로그인이 거절한 것입니다.
- `request` 이면 대개 오래 열어 둔 로그인 탭에서 진행한 것입니다. 처음부터 다시 로그인하면 됩니다.
- `config` 이면 우리 설정(환경변수)이 빠진 것입니다. 허브 담당자가 고칩니다.

**다른 서비스에서 "서비스 이동 버튼"을 누르면 모든 서비스가 다 보인다**

- 고장이 아닙니다. 허브에 로그인하지 않았거나, 브라우저가 다른 사이트의 쿠키를 막아서 권한 정보를 못 받은 경우입니다.
- 실제 접근 권한은 각 서비스가 따로 검사합니다.

**다른 서비스에서 "서비스 이동 버튼"이 아예 안 뜬다**

- 확인: `https://service-hub.dvi-ind.com/switcher.js` 가 열리는지 봅니다.
- 열리면 그 서비스의 페이지에 스크립트가 제대로 붙어 있는지 그 서비스 담당자가 확인합니다.
- 안 열리면 정적 파일 서버(`api.dvi-ind.com`) 담당자에게 넘깁니다.

## 2. 배포하기

1. `dev` 브랜치에 push 합니다. Vercel 이 빌드해서 1~2분 안에 운영에 냅니다.
2. 빌드가 끝나면 저장소 루트에서 점검 스크립트를 돌립니다.

   ```bash
   pnpm --filter @dvi/web smoke
   ```

   로그인 없이 운영 허브의 주요 길목 8곳을 확인합니다. 결과는 한 줄씩 `[통과]` 또는 `[실패]` 로 나옵니다.

   | 확인하는 것 | 실패하면 의심할 것 |
   | --- | --- |
   | 가동 감시 주소가 정상인가 | Keycloak, 허브 서버, 환경변수 |
   | 로그인 없이 연 페이지가 세션 갱신으로 가는가 | 로그인 검사(middleware) |
   | 로그인 없이 부른 API 가 정해진 모양의 401 을 주는가 | 로그인 검사(middleware) |
   | 화면 파일(`/assets`)이 로그인 검사에서 빠져 있는가 | 로그인 검사 설정 |
   | Keycloak 이 이 주소로 돌아오는 로그인을 받아 주는가 | Keycloak 의 주소 등록 |
   | 서비스 워커, 매니페스트, switcher.js 가 열리는가 | 정적 파일, 정적 파일 서버 |
   | 보안 헤더가 붙어 있는가 | `vercel.json` |
   | 예전 주소가 새 주소로 넘어가는가 | 로그인 검사(middleware) |

3. 사람이 직접 한 번 열어 봅니다. 로그인한 뒤 홈 위젯이 채워지는지, 설정 화면이 열리는지 봅니다.
4. 점검에 `[실패]` 가 있거나 화면이 깨졌으면 [3. 되돌리기](#3-되돌리기)를 합니다.

## 3. 되돌리기

Vercel 대시보드에서 이전 배포로 바로 되돌릴 수 있습니다(Instant Rollback).

1. Vercel 대시보드에서 허브 프로젝트를 엽니다.
2. **Deployments** 탭에서 마지막으로 멀쩡했던 Production 배포를 찾습니다.
3. 오른쪽 `...` 메뉴에서 **Instant Rollback** 을 누릅니다. 몇 초 안에 운영 주소가 그 배포로 바뀝니다.

되돌린 뒤에 알아 둘 것:

- 되돌린 상태에서는 새로 push 해도 운영에 자동으로 반영되지 않습니다. 고친 배포를 확인한 뒤 대시보드에서 직접 **Promote** 합니다.
  (Vercel 의 동작을 기준으로 쓴 내용입니다. 처음 되돌릴 때 화면에서 한 번 확인해 주세요.)
- 사용자 기기에 깨진 화면이 이미 저장돼 있으면, 되돌려도 그 기기에서는 바로 안 풀릴 수 있습니다. 그때는 [6. 서비스 워커 긴급 정지](#6-서비스-워커-긴급-정지)를 합니다.

## 4. 로그인이 유지되는 방식

문의를 해석할 때 필요한 만큼만 적습니다.

- 허브의 로그인(세션)은 **10분**짜리입니다. 일부러 짧게 두었습니다.
- 10분이 끝나기 전에 허브가 통합 로그인(Keycloak)에 "이 사람 아직 로그인돼 있나요?"라고 물어 세션을 늘립니다.
  이 갱신은 **`/api/auth/refresh` 한 곳에서만** 합니다. 갱신용 열쇠(refresh token)는 한 번만 쓸 수 있어서, 두 곳에서 동시에 쓰면 하나가 실패하기 때문입니다.
- 화면을 열어 두면 끝나기 2분 전에 알아서 늘립니다. 탭이 여러 개면 한 번에 한 탭씩 차례로 늘립니다.
  다만 세션이 끝난 뒤 새로 여는 페이지(탭 여러 개를 한꺼번에 복원할 때 등)는 이 순서 밖에서 늘리므로, 그중 하나만 성공하고 나머지는 거절될 수 있습니다.
- 통합 로그인이 갱신을 거절하면(퇴사, 통합 로그인 만료, 위의 겹친 갱신 등) 허브는 통합 로그인 화면으로 보냅니다.
  통합 로그인이 아직 살아 있으면 화면 없이 바로 돌아옵니다. 이때 로그인 정보는 지우지 않습니다. 겹친 갱신에서 다른 탭이 방금 받은 새 로그인 정보를 지우지 않기 위해서입니다.
- 로그인을 여러 탭에서 동시에 시작해도 서로 방해하지 않습니다. 탭마다 로그인 진행 정보를 따로 둡니다(`hub_auth.<임의 문자열>`, 10분).
- 통합 로그인에 다녀온 지 1분 안에 또 거절되면, 계속 오가지 않도록 멈추고 "로그인을 이어가지 못했습니다"를 띄웁니다.
- **퇴사나 권한 변경은 늦어도 10분 안에** 허브에 반영됩니다.

로그인 정보는 아래 쿠키에 담깁니다. 모두 화면 스크립트에서 읽을 수 없게(HttpOnly) 되어 있습니다.

| 쿠키 | 담긴 것 | 유효 기간 |
| --- | --- | --- |
| `hub_session` | 이름, 이메일, 권한 (허브 서버도 이 쿠키로 사람을 확인합니다) | 10분 |
| `hub_rt` | 세션을 늘릴 때 쓰는 열쇠(refresh token) | 통합 로그인이 살아 있는 동안 |
| `hub_idt` | 전체 로그아웃에 쓰는 값 | 통합 로그인이 살아 있는 동안 |
| `hub_access` | 서비스 이동 버튼이 쓰는 권한 정보 | 통합 로그인이 살아 있는 동안 |

## 5. 로그 읽기

### 5.1 브라우저 콘솔

API 요청이 실패하면 운영 화면에서도 콘솔에 빨간 줄이 하나 남습니다.

```
401 GET /api/hub/notices UNAUTHORIZED from=hub-web(expired) 8ms #a1b2c3d4 vercel=icn1::... — 로그인이 필요합니다.
```

앞에서부터 이렇게 읽습니다.

1. `401 GET /api/hub/notices`: 응답 상태와 요청 주소입니다. 서버까지 가지 못했으면 숫자 대신 `ERR` 가 나옵니다.
2. `UNAUTHORIZED`: 오류 코드입니다.
3. `from=hub-web`: **오류를 낸 곳**입니다.

   | from | 뜻 |
   | --- | --- |
   | `network` | 서버까지 가지 못했습니다. 사용자의 인터넷 연결 문제입니다 |
   | `vercel` | Vercel 이 직접 낸 오류입니다. 허브 서버에 닿지 못한 경우 등입니다 |
   | `hub-web` | 허브의 로그인 검사나 로그인 기능이 낸 오류입니다. Vercel 로그에서 찾습니다 |
   | `hub-server` | 허브 서버가 낸 오류입니다. 허브 서버 로그에서 찾습니다 |
   | `app` | 화면 코드가 직접 낸 오류입니다 |

4. `(expired)`: 로그인 검사가 막은 이유입니다. `none` 은 로그인 정보가 없음, `expired` 는 10분이 지남, `invalid` 는 로그인 정보가 위조됐거나 깨짐입니다.
5. `#a1b2c3d4`: 요청 번호입니다. **Vercel 로그를 찾을 때 이 번호를 씁니다.**
6. `vercel=...`: Vercel 이 붙인 값입니다. 참고만 합니다. Vercel 로그 검색에 쓸 수 있다는 보장은 없습니다.

알아 둘 것:

- 세션이 끝나서 한 번 늘리고 다시 성공한 경우에도 빨간 401 줄이 하나 남습니다. 화면이 멀쩡하면 신경 쓰지 않아도 됩니다.
- 세션 갱신에 실패하면 `[api] 세션 갱신 거절(401) from=hub-web #...` 같은 노란 줄이 남습니다.
- 요청과 응답 내용까지 자세히 보려면 콘솔에 `portalApiLog.set('debug')` 를 입력합니다. 원래대로 돌리려면 `portalApiLog.reset()` 입니다. 그 브라우저에만 적용됩니다.

### 5.2 Vercel 로그

Vercel 대시보드에서 허브 프로젝트를 열고 **Logs** 탭으로 갑니다. 허브는 로그를 한 줄짜리 JSON 으로 남깁니다.

```json
{"event":"refresh.rejected","who":"keycloak","rid":"9f8e7d6c","status":400,"error":"invalid_grant","detail":"Session not active"}
```

검색창에 이렇게 넣어 찾습니다.

- 브라우저에서 받은 요청 번호(예: `a1b2c3d4`): 그 요청에 대한 서버 기록이 나옵니다.
- `"who":"config"`: 우리가 고쳐야 할 설정 문제만 나옵니다.
- `health.down`: 가동 감시가 발견한 장애만 나옵니다.

`who` 는 누구 쪽 문제인지를 나타냅니다.

| who | 뜻 |
| --- | --- |
| `user` | 로그인이 끝났을 뿐인 정상적인 흐름입니다 |
| `keycloak` | 통합 로그인이 거절했거나 응답하지 않습니다 |
| `hub-server` | 허브 서버가 멈췄거나 응답하지 않습니다 |
| `config` | 우리 설정(환경변수) 문제입니다 |
| `request` | 요청이 잘못됐습니다. 오래된 로그인 탭이나 깨진 쿠키처럼 원인을 하나로 정할 수 없는 경우도 여기에 들어갑니다 |

`event` 는 무슨 일이 있었는지를 나타냅니다.

| event | 언제 남나 |
| --- | --- |
| `session.invalid` | 로그인 정보의 서명이 맞지 않을 때. 한 사람이면 쿠키가 깨진 것이고, **모든 사람에게 한꺼번에 나오면 `SESSION_SECRET` 이 바뀐 것**입니다 |
| `session.no_secret` | Vercel 에 `SESSION_SECRET` 이 설정돼 있지 않을 때 |
| `refresh.missing` | 갱신용 열쇠가 없을 때. 통합 로그인에 한 번 다녀오면 해결됩니다 |
| `refresh.rejected` | 통합 로그인이 갱신을 거절했을 때. `detail` 에 이유가 있습니다 |
| `refresh.unreachable` | 통합 로그인에 닿지 못했을 때. 이때는 세션을 지우지 않습니다 |
| `refresh.no_claims` | 갱신 응답에 계정 정보가 없을 때. Keycloak 설정 문제입니다 |
| `auth.config_missing` | 갱신에 필요한 환경변수가 없을 때 |
| `auth.error_page` | "로그인하지 못했습니다" 화면이 나갔을 때. `title` 과 `detail` 에 내용이 있습니다 |
| `login.retry_expired` | 로그인 탭을 여러 개 열어서 생긴 오류를 자동으로 한 번 다시 시도했을 때 |
| `health.down` | 가동 감시가 장애를 발견했을 때. `check` 에 무엇이 멈췄는지 있습니다 |

일부러 남기지 않는 것도 있습니다.

- 세션 갱신 성공, 그리고 단순히 10분이 지나서 생긴 401 은 남기지 않습니다. 양만 많고 쓸모가 적기 때문입니다.
- 토큰이나 쿠키 값은 남기지 않습니다.
- 주소창으로 들어온 값은 짧은 코드 형태만 남기고, 긴 문장이면 `other` 로 바꿔 남깁니다.

그래서 **허브 서버 API(`/api/hub`)가 401 인데 Vercel 로그에 아무 줄이 없다면, 허브 서버가 낸 401** 입니다.

### 5.3 로그는 얼마나 남나

Vercel 로그는 요금제에 따라 **1시간에서 1일** 정도만 남습니다. **[정해 주세요]** 현재 요금제를 확인합니다.
며칠 지난 문의까지 추적하려면 Vercel 의 **Log Drain** 기능으로 로그를 다른 저장소에 보내야 합니다.

## 6. 서비스 워커 긴급 정지

허브는 홈 화면 아이콘으로 열 때 빨리 뜨도록 화면 파일을 기기에 저장해 둡니다. 이 일을 서비스 워커(`public/sw.js`)가 합니다.
깨진 화면이 저장돼 버리면 Vercel 에서 되돌려도 그 기기에서는 안 풀릴 수 있습니다. 그때 이 절차로 모든 기기의 저장본을 지웁니다.

**정지하기**

```bash
cp apps/web/scripts/sw-kill.js apps/web/public/sw.js
git commit -am "chore(web): 서비스 워커 긴급 정지"
git push
```

사용자가 다음에 허브를 열면, 저장해 둔 화면을 모두 지우고 서버에서 새로 받아 한 번 다시 엽니다.
같은 화면을 계속 새로고침하는 일은 생기지 않습니다.

**원래대로 돌리기**

하루나 이틀 지나 다들 한 번씩 열었을 즈음, 정지하기 전의 파일로 되돌려 다시 배포합니다.

```bash
git checkout <정지하기 전 커밋> -- apps/web/public/sw.js
git commit -m "chore(web): 서비스 워커 되살리기"
git push
```

## 7. 비밀값 바꾸기

| 비밀값 | 넣는 곳 | 바꾸면 생기는 일 |
| --- | --- | --- |
| `SESSION_SECRET` | Vercel 과 허브 서버 **두 곳에 같은 값** | 모든 사람이 한 번 다시 로그인합니다. 통합 로그인이 살아 있으면 화면 없이 지나갑니다 |
| `OIDC_CLIENT_SECRET` | Vercel 과 Keycloak | 바꾸는 사이에는 로그인과 갱신이 실패합니다 |
| `OIDC_ISSUER`, `OIDC_CLIENT_ID` | Vercel | 거의 바꿀 일이 없습니다 |

### SESSION_SECRET 바꾸는 순서

1. 새 값을 만듭니다.

   ```bash
   openssl rand -base64 48
   ```

2. Vercel 환경변수와 허브 서버 설정에 **같은 값**을 넣습니다.
3. Vercel 재배포와 허브 서버 재시작을 **되도록 같은 시각에** 합니다.
   한쪽만 바뀐 동안에는 위젯이 401 을 내고, Vercel 로그에 `session.invalid` 가 쏟아집니다.
4. `pnpm --filter @dvi/web smoke` 를 돌리고, 직접 로그인해서 위젯이 채워지는지 확인합니다.

### OIDC_CLIENT_SECRET 바꾸는 순서

1. Keycloak 담당자와 시각을 맞춥니다.
2. Keycloak 에서 새 값을 만들면 바로 Vercel 에 넣고 재배포합니다.
3. 점검 스크립트와 직접 로그인으로 확인합니다.

## 8. 가동 감시

아래 주소는 로그인 없이 열리며, 허브가 기대는 세 곳이 살아 있는지 알려 줍니다.

```
https://service-hub.dvi-ind.com/api/health
```

모두 정상이면 200 과 함께 이렇게 나옵니다.

```json
{"status":"ok","checks":{"config":"ok","keycloak":"up","hubServer":"up"}}
```

하나라도 문제가 있으면 503 과 함께 무엇이 멈췄는지 나옵니다.

```json
{"status":"down","checks":{"config":"ok","keycloak":"down (timeout)","hubServer":"up"}}
```

- `config`: 우리 환경변수가 모두 있는지
- `keycloak`: 통합 로그인이 응답하는지
- `hubServer`: 허브 서버가 정상이라고 답하는지

각 항목은 5초 안에 답이 없으면 멈춘 것으로 봅니다.

**감시 등록하기**: UptimeRobot 같은 외부 감시 서비스(무료, 5분 간격)에 이 주소를 등록하고 알림을 걸어 둡니다.
**[정해 주세요]** 알림을 받을 사람.

## 9. 주소와 연결된 설정

### Keycloak 에 등록돼 있어야 하는 주소

클라이언트 `service-hub` 의 설정입니다.

| 설정 항목 | 값 | 확인 여부 |
| --- | --- | --- |
| Valid redirect URIs | `https://service-hub.dvi-ind.com/api/auth/callback` | 확인함 (점검 스크립트가 매번 확인합니다) |
| Valid post logout redirect URIs | `https://service-hub.dvi-ind.com/` | 확인함 (2026-11-25) |
| 계정 화면에서 돌아오는 주소 | `https://service-hub.dvi-ind.com/` | **확인 필요** |

계정 화면 주소는 허브의 설정 화면에서 "로그인 방법"을 눌러 계정 화면으로 간 뒤, "돌아가기"를 눌러 허브로 돌아오는지 보면 됩니다.

예전 주소(`dvi-service-hub.vercel.app`)의 등록은 당분간 지우지 않습니다. 로그인 도중이던 사람과 예전 앱이 쓸 수 있습니다.

### 서비스 이동 버튼(switcher.js) 올리기

허브 주소나 서비스 목록(`src/features/systems/lib/services.ts`)이 바뀌면 이 파일을 다시 만들어 올려야 합니다.
허브 배포에 포함되지 않으니 따로 올려야 합니다.

1. 파일을 만듭니다.

   ```bash
   cd apps/web
   pnpm exec vite build -c vite.switcher.config.ts
   ```

2. 만들어진 `apps/web/dist/switcher.js` 를 `api.dvi-ind.com/static/switcher/` 에 올립니다. 버전 태그를 붙이는 방법은 `docs/RADME.md` 에 있습니다.
3. 다른 서비스가 스크립트 태그에 허브 주소를 직접 적어 두었다면(`data-hub="..."`) 새 주소로 바꿔 달라고 알립니다.

### 모바일 앱

앱이 띄우는 주소는 `apps/mobile/capacitor.config.ts` 의 `server.url` 에 있습니다. 이 값을 바꾸면 앱(APK)을 다시 만들어 배포해야 합니다.
예전 주소를 띄우는 앱도 새 주소로 자동으로 넘어가기 때문에 사용은 가능합니다.

## 11. 아직 확인하지 못한 것

배포한 뒤 실제 환경에서 한 번씩 확인해야 합니다.

- Vercel 로그에서 요청 번호(`rid`)로 실제로 찾아지는지.
- 경고(warn) 로그가 Vercel 의 필터에서 warning 으로 잡히는지. 경우에 따라 error 로 잡힐 수 있습니다.
- 갱신 거절 이유(`refresh.rejected` 의 `detail`)가 이 문서의 예시와 같은 문구로 나오는지.
- 서비스 워커 긴급 정지를 실제로 해 본 적은 없습니다.
- 모바일 앱에서 Google 로그인이 끝까지 되는지.
